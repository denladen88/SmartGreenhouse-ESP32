# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

.NET 8 ASP.NET Core backend (Web SDK, not a plain worker service) for the SmartPlant/SmartGreenhouse system. It subscribes to MQTT telemetry published by the ESP-32 firmware (sibling project, see `../ESP-32/CLAUDE.md`), persists it to SQLite, periodically runs an "AI Agronomist" cycle (pulls a recent sensor trend plus a live photo from the ESP32-CAM, sends both to Google Gemini for analysis, publishes the resulting pump/fan/light/heater decision back over MQTT), and exposes an HTTP + SignalR API consumed by two companion clients — a mobile app (`../MobileApp`, React Native/Expo) and a web control panel (`../WebApp`, React/Vite) that this same process also serves as static files — for live monitoring and manual control.

## Build / run commands

Standard .NET CLI, run from `Backend/`:

```
dotnet build                       # build
dotnet run                         # run (binds 0.0.0.0:5080 in Development per launchSettings.json — reachable from other LAN devices, e.g. a phone running the MobileApp)
dotnet ef migrations add <Name>    # add an EF migration after changing an entity in Models/
```

No test project exists yet. There is no separate lint config — rely on the C# compiler/analyzers via `dotnet build`.

## Required local config (not in git)

Configuration is layered `appsettings.json` → `appsettings.Development.json` → user secrets (`UserSecretsId` is set in the `.csproj`), bound to strongly-typed `Options` classes in `Models/` via `builder.Services.Configure<T>(...)` in `Program.cs`:

- `Mqtt` → `MqttOptions` — broker address/port/credentials and topics (`Topic` for inbound telemetry, `CommandsTopic` for outbound AI decisions). Must match the ESP-32 firmware's `MQTT_TELEMETRY_TOPIC`/`MQTT_COMMANDS_TOPIC` in `Config.h` — both currently use `smartplant/telemetry` and `smartplant/commands`.
- `Gemini` → `GeminiOptions` — Gemini API key + model name.
- `Esp32` → `Esp32Options` — HTTP URL of the ESP32-CAM still-capture endpoint.
- `AiAgronomist` → `AiAgronomistOptions` — local hour-of-day for the once-daily profile review (`DailyAnalysisHour`), photo-retry interval/window for that review, local-control fallback interval, and trend window/bucket sizes (minutes).
- `Plant` → `PlantOptions` — fallback plant name/care notes used only when the `Plantings` table is empty (fresh DB, never onboarded through the mobile app yet). Once a `Planting` row exists, it takes over as the source of truth — see Architecture below.
- `Api` → `ApiOptions` — shared `Key` checked by `ApiKeyMiddleware` against the `X-Api-Key` header (or `?access_token=` for the SignalR handshake) on every `/api/*` and `/hubs/*` request. There is no per-user auth — this is a single shared secret, acceptable only because the API is meant to stay on the local Wi-Fi network, not exposed to the internet.

**`appsettings.json` currently contains a live Gemini API key in plaintext and is not gitignored** (only `.env` and `*.db*` are ignored). The `UserSecretsId` is already configured, so secrets should be moved into `dotnet user-secrets` (or an environment-specific file that *is* gitignored) rather than committed `appsettings.json`.

## Architecture

`Program.cs` wires up a `WebApplication` (`Microsoft.NET.Sdk.Web`) with two long-running `BackgroundService`s, a `DbContext`, MVC controllers, a SignalR hub, and static-file hosting for `../WebApp`. `ApiKeyMiddleware` gates `/api` and `/hubs`; `/capture`-style ESP32 endpoints aren't part of this backend (that's the firmware's own HTTP server).

Also serves `../WebApp` (React/Vite web control panel): `UseStaticFiles()` + `MapFallbackToFile("index.html")` serve a built SPA from `wwwroot/` (gitignored — copy `WebApp`'s `npm run build` output there), so opening `http://<this-host>:5080/` in any browser on the LAN shows the same dashboard/controls/history as the mobile app, no separate web server needed. `AddCors`/`UseCors` (`AllowAnyOrigin`, since auth is the `X-Api-Key` header, not a cookie) exists only so `WebApp`'s own Vite dev server (a different origin/port) can call this API during that project's development — CORS is irrelevant once `WebApp` is built into `wwwroot` and served same-origin. The `.csproj` has an explicit `<Content Update="wwwroot/**/*" CopyToOutputDirectory="PreserveNewest" />` because `Sdk.Web`'s default only copies `wwwroot` on `dotnet publish`, not `dotnet build`/`dotnet run` — and `ContentRootPath` here is pinned to the build output dir (see below), not the source tree, so without that line local `dotnet run` would never find the SPA.

- **AppDbContext** (`Data/AppDbContext.cs`) — `DbSet`s for `TelemetryRecord`, `AiDecisionRecord`, `PlantProfile`, `Planting`; SQLite file `greenhouse.db` in the working directory (`Data Source=greenhouse.db`, hardcoded fallback in `OnConfiguring` — relative to the process's current directory, **not** `ContentRootPath`, so always `dotnet run`/launch from `Backend/` or you'll create/migrate a stray db elsewhere). Schema is applied via real EF Core migrations (`Migrations/`, `db.Database.Migrate()` in `Program.cs`) — add a migration with `dotnet ef migrations add <Name>` after changing any entity.

- **MqttBackgroundService** (`Services/MqttBackgroundService.cs`) — owns the MQTT connection (MQTTnet `IManagedMqttClient`, auto-reconnect). Subscribes to `MqttOptions.Topic`, deserializes each message as `TelemetryMessage` (snake_case JSON matching the ESP-32 firmware's payload shape), logs it, persists it as a `TelemetryRecord`, and broadcasts it to connected SignalR clients (`"TelemetryReceived"` on `TelemetryHub`). It's registered as both a singleton and the `IMqttPublisher` implementation (`AddSingleton<IMqttPublisher>(sp => sp.GetRequiredService<MqttBackgroundService>())`), so other services/controllers can publish outbound MQTT messages (e.g. AI commands, manual overrides) through the same managed client without re-implementing connection handling.

- **AiAgronomistService** (`Services/AiAgronomistService.cs`) — a `BackgroundService` (also registered as a plain singleton so `PlantingController` can inject the same instance and call `TriggerImmediateProfileAnalysisAsync`) running two independent loops via `Task.WhenAll`. **Profile supervision loop**: exactly once a day at `AiAgronomistOptions.DailyAnalysisHour` local time (wall-clock schedule via `TimeUntilNextNoon`; catches up on startup if that hour already passed today and no review has run since, per `AlreadyReviewedSinceTodayNoonAsync`). It reads `TelemetryRecord`s from the last `TrendWindowMinutes`, a summary of what the local controller did since the last review, the current planting context (planted date, days since, soil, notes — sent every time), and fetches a JPEG from the ESP32-CAM. The scheduled review **requires** a photo: if none is available it retries every `PhotoRetryIntervalMinutes` until `PhotoRetryWindowMinutes` elapse, then skips that day leaving the profile untouched. It sends all of it to the Gemini `generateContent` API asking it to (re)set the ideal parameter ranges plus assess the plant's `GrowthStage` — persisted as a `PlantProfile` row and broadcast as `"PlantProfileReceived"`. There is one exception to the daily cadence: a **bootstrap** run fires immediately when no `PlantProfile` exists yet for the current plant (fresh DB, or a new `Planting` with a changed name started via the mobile app — `TriggerImmediateProfileAnalysisAsync` no-ops if a profile already exists); bootstrap does **not** require a photo. There is no longer any anomaly-triggered early review. **Local control loop**: every `LocalControlIntervalMinutes` (no AI call), it reads the current `PlantProfile` plus recent telemetry and decides pump/fan/light/heater with simple rules (sustained-reading fan threshold, declining-trend-plus-cooldown pump rule, ambient-Lux-shortfall light rule, soil-temp-deficit heater rule), logs an `AiDecisionRecord`, broadcasts it as `"DecisionReceived"`, and republishes the resulting `AiCommand` via `IMqttPublisher` to `MqttOptions.CommandsTopic` every tick regardless of change (the ESP32's `FAN_MAX_RUNTIME_MS`/pump/heater failsafes rely on that repetition). Both loops resolve the "current" plant via `GetCurrentPlantingAsync`/`ResolvePlantName` — the most recent `Planting` row, falling back to static `PlantOptions.Name` only if none exists yet.

- **Controllers/** — thin REST surface for the mobile app, all behind `ApiKeyMiddleware`: `TelemetryController` (`GET /api/telemetry/latest|history`), `CommandsController` (`POST /api/commands` — manual actuator override, logs an `AiDecisionRecord` with `Reason="Manual override via mobile app"` and publishes to MQTT exactly like the AI's own decisions, so it's naturally superseded by the next local-control tick), `PlantProfileController` (`GET/PUT /api/plant-profile` — the most recently-updated profile), `DecisionsController` (`GET /api/decisions/history`), `CameraController` (`GET /api/camera/snapshot` — proxies `Esp32Options.CameraUrl` so the app never needs a direct route to the ESP32), `PlantingController` (`GET /api/planting/current`, `POST /api/planting` — onboarding a new planting; fires `AiAgronomistService.TriggerImmediateProfileAnalysisAsync` in the background, not awaited, since a Gemini call can take tens of seconds).

- **Hubs/TelemetryHub.cs** — empty SignalR hub (`/hubs/live`); clients only receive, they never call server methods. Server-side broadcasts happen from `MqttBackgroundService` and `AiAgronomistService` as described above.

- **Models/** — plain POJOs/records split between MQTT wire types (`TelemetryMessage`, `AiCommand` — `JsonPropertyName`-annotated snake_case to match the ESP-32/MQTT side), the EF entities (`TelemetryRecord`, `AiDecisionRecord`, `PlantProfile`, `Planting`), the Gemini response DTOs (nested private records inside `AiAgronomistService`), and the `*Options` config-binding classes described above.

**Cross-project notes**:
- The ESP-32 firmware (`MqttService`, wired up in its `main.cpp`) subscribes to `MQTT_COMMANDS_TOPIC` and applies `pump_on`/`fan_on`/etc. directly to `ActuatorService`, so both `AiAgronomistService`'s and `CommandsController`'s published commands on `smartplant/commands` reach the device the same way. The pump still has an independent 5s failsafe timeout on the firmware side regardless of command source.
- `../MobileApp` (React Native/Expo, TypeScript) and `../WebApp` (React/Vite, TypeScript) are the two HTTP/SignalR clients for everything in `Controllers/`+`Hubs/` above — see their own CLAUDE.md for the client-side architecture (deliberately near-identical between the two). Both are LAN-only by design (no JWT/OAuth, no public HTTPS), matching the single shared `Api:Key`.
